## Phase 0 — Skeleton
*July 2026*

Phase 0 turned the planning-only repo into a project that actually runs. It scaffolded the mobile app from Expo's SDK 57 default template, stripped the demo screens down to a minimal root layout and placeholder home screen, and locked in the project's code standards as enforced tooling: strict TypeScript, ESLint with the required rule set, Prettier, and the @/* path alias into src/. The backend came up as a local Supabase stack in Docker, shifted to its own port range so it coexists with Shot O'Clock's local stack, with the app reading its connection from environment variables and proving connectivity through a health check surfaced on the home screen. Two toolchain incompatibilities in Expo's lint config were worked around and pinned (D022), and the decision to develop local-first against Docker rather than block on a hosted Supabase project was made autonomously and logged as D021 — the one call in this phase that needed follow-up beyond the build itself, since a hosted project had to exist before Phase 3.

## Phase 1 — Full database schema
*July 2026*

Phase 1 gave Callout its entire data model in one pass, before any screen or game logic exists, so that no later phase ever needs a migration to add a concept — only to activate logic against fields that already exist. One migration created all nine enums and nine tables (profile plus the eight game tables), encoding the locked rules structurally where the database can hold them: role and status as independent membership fields, composite foreign keys guaranteeing a turn's target is a member of that exact group, and partial unique indexes enforcing one host per group, one in-progress round per group, and one pending turn per round. A second migration put Row Level Security on every table, built around SECURITY DEFINER helper predicates that check membership status without recursing, and revoked write privileges on all game tables outright so the client-writes-nothing rule holds at the privilege layer beneath the policies. A 53-test pgTAP suite, runnable via npm run test:db, verified every visibility tier and the write posture against a fresh database. The phase surfaced four gaps the planning documents hadn't closed, each resolved as a logged judgment call: a profile table the data model never named but three existing decisions implicitly required (D023), a notification table generalized beyond turn scope to cover the committed trigger list (D024), read visibility for invited-but-not-yet-accepted members (D025), and the three columns recurring cadence actually needs to survive DST math (D026).

## Phase 2 — Auth + app shell
*July 2026*

Phase 2 turned the schema-only project into an app a person can actually open, sign into, and walk around in. Supabase Auth became real: sign-up collects a display name alongside email and password and passes it through user metadata to the Phase 1 trigger, so every new account arrives with its profile row already in place, and sessions persist across app restarts through AsyncStorage-backed storage with token refresh tied to the app being foregrounded. Routing was split into session-guarded groups, so signing in or out swaps the entire navigation tree without any screen ever manually redirecting, and the splash screen holds until both fonts and the persisted session are restored. On top of that landed the full six-screen shell from the design prototype — home, create group, join, group detail, my turn, and pick next — rebuilt natively in React Native from the prototype's layout and visual language (its palette, Outfit and Plus Jakarta Sans typefaces, and component boundaries were extracted into a shared theme and component set), with every game action a placeholder over static data until Phase 3 activates the real relay. The live flow was verified against the local stack end to end: sign-up, trigger-created profile, the profile self-update surface, cross-user write denial, sign-out, and sign-in all pass, and the whole app typechecks, lints, and bundles cleanly.

## Phase 3 — MVP core loop
*July 2026*

Phase 3 made the relay loop real, end to end. All game logic landed in Postgres as SECURITY DEFINER RPC functions — create a group, invite, accept or decline, start the game, submit a turn, call out the next player, skip, remove — with fairness enforced inside every pick path by querying membership against turns-this-round, structured error codes on every rejection, and each transition serialized on a group-row lock so concurrent clients and the scheduled job cannot double-advance. Deadline enforcement became genuinely server-side: a pg_cron job runs every minute, marks expired pending turns missed, system-picks successors for stalled hand-offs, and rolls completed rounds straight into the next one, so the relay keeps moving with no client awake and no human intervening. Three relay rules the planning documents bounded but never pinned down were composed from existing decisions and logged rather than improvised silently: system-random picks at round start and after misses (D029), the submit-then-pick hand-off sharing the turn's single deadline window (D029), and RPC-backed user search for invites (D030). On the client, the placeholder shell became a live app — a typed RPC layer, RLS-filtered reads assembled into view bundles, Realtime subscriptions per group, and countdowns rendered strictly as deadline_at minus a synced server clock — across all six screens plus a new host invite screen. The phase closed with an 89-test pgTAP suite on the RPC layer and a 25-check end-to-end run driving three real accounts through the full loop — first against the live local stack, then repeated against the hosted Supabase project after its migrations and auth config were pushed at close-out, both including the actual cron job resolving an expired turn. The hosted push resolved D021 and caught one environment difference worth remembering: hosted default table privileges are not the local stack's, so client grants are now explicit rather than inherited.

## Phase 3B — Identity & Connections
*July 2026*

Phase 3B gave users a real identity and rebuilt how people find each other — three times over, because getting the social model right took correction rounds the phase absorbed on its open PR rather than deferring. The stable core landed first: every profile gained a high-entropy shareable Callout ID, a connections graph with automatic pairwise connection on group acceptance (recorded in a once-per-pair-per-group ledger so a deliberately removed connection stays removed until a genuinely new shared group), phone sign-up/sign-in via SMS one-time code with no password (verified against the local test-OTP map, with the hosted provider deferred to Kashawn per D043), second-method linking from the profile, and D042's five-minute pick window on the relay. The first invite model gated group invites behind connections; Kashawn's review flagged the inversion — connections are a convenience layer, never a gate — and D047–D058 rebuilt it around exact-match global search, a three-step creation flow, the persistent group join code with host-approved requests once a game is running, and token-based share links. A second review pass then simplified what the first correction had grown: D059–D067 retired the token system entirely in favor of the join code as the one sharing mechanism, removed email as a lookup key anywhere (the exact Callout ID, searched on a deliberate tap rather than as-you-type, is the only global key), restored the pickers to a connections-first default with live name filtering, and made the group link pre-fill Join Group rather than auto-submit — with already-members skipping straight into the group on an informational toast, and the profile share reduced to a plain download link pointed at kashawnbrown.com until a store listing exists. Along the way the profile picked up a user-selectable avatar color: tapping the pencil-badged avatar opens a picker over an eight-color palette, stored on the profile and resolved everywhere, with unpicked users keeping their hash-assigned default. The phase closed at 208 pgTAP tests across the reworked suites and green end-to-end runs on both stacks (37/37 local including both D041 linking flows through their real confirmation channels, 24/24 hosted), with every migration live on the hosted project.
